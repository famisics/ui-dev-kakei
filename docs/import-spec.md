# カード明細インポート仕様

## 1. 目的

手入力した取引とカード明細を同じ家計簿取引として管理し、対応する手入力取引がない明細だけを
新しい取引として作成する。同じ月の累積明細を月途中・月末などに繰り返しインポートしても、
取引が重複しないことを保証する。

カード会社が出力するファイルは、対象時点までの明細をすべて含む累積型として扱う。増分型の
ファイルは対象外とする。

## 2. 用語

- **取込元**: カード会社ごとのファイル形式の設定。
- **取引**: 家計簿に表示・集計する収支。手入力またはインポートによって作成される。
- **明細エントリー**: インポートファイルに含まれるカード明細1件。取引とは分けて保存し、
  対応する取引へ1対1で紐付ける。
- **累積スナップショット**: 月途中・月末など、出力時点までの同じ明細を繰り返し含むファイル。
- **フィンガープリント**: 日付・金額・種別・正規化した明細名が同じ明細をまとめるための値。
- **`entry_key`**: 同じ明細エントリーを再登録しないための永続的な一意キー。
- **`occurrence`**: 同じフィンガープリントを持つ明細が複数ある場合の1始まりの出現番号。

## 3. データモデル

### `import_sources`

既存の取込元をそのまま使う。

- 表示名の変更では `id` を変更しない。
- 取込履歴がある取込元は削除せず、必要になった場合は無効化する。

### `transactions`

既存の取引をそのまま使う。カード/現金といった支払元の区別は設けず、すべての手入力取引を
カード明細の照合対象とする。

- `source` は取引が最初に作成された経路を表す。
- 手入力取引へカード明細を紐付けても `source = 'manual'` を維持する。
- インポートから新規作成した取引は `source = 'import'` とする。

### `statement_entries`

インポートしたカード明細の同一性と取引への紐付けを管理する。

- `id uuid primary key`
- `user_id uuid not null`
- `import_source_id uuid not null references import_sources(id)`
- `transaction_id uuid not null references transactions(id)`
- `entry_key text not null`
- `fingerprint text not null`
- `occurrence integer not null check (occurrence > 0)`
- `external_id text nullable`
- `date date not null`
- `amount numeric not null check (amount > 0)`
- `type text not null check (type in ('income', 'expense'))`
- `description text not null`
- `created_at timestamptz not null`

次の一意制約を設ける。

```sql
unique (user_id, import_source_id, entry_key)
unique (transaction_id)
```

1つの取引に複数のカード明細を紐付けず、1つの明細を複数回登録しない。

### `import_batches`

インポート操作ごとの結果を保存する。

- 既存項目に `matched_count`、`created_count`、`duplicate_count` を追加する。
- 同じファイルを再度指定した操作も監査履歴として保存してよい。
- 冪等性はバッチ行数ではなく、`transactions` と `statement_entries` が増えないことで保証する。

## 4. 明細の一意性

### 4.1 フィンガープリント

カード会社固有の取引IDがない明細では、次の値からフィンガープリントを生成する。

```text
fingerprint = SHA-256(
  date |
  amount |
  type |
  normalize(description)
)
```

`normalize(description)` は既存の明細名正規化を使用する。金額は常に正数とし、収入・支出は
`type` で区別する。

### 4.2 `occurrence`

1つの累積スナップショット内で、同じフィンガープリントを持つ明細をファイルの出現順に
`1, 2, 3, ...` と採番する。同じフィンガープリントの明細は内容上区別できないため、
`occurrence` は個々の決済を特定する番号ではなく、累積件数を表す番号として扱う。

同じ取込元に複数のファイルを同時に指定した場合は、ファイルごとに `occurrence` を
採番したうえで、フィンガープリントと `occurrence` の組が同じ行を1件にまとめる。
各ファイル内の `occurrence` は1始まりの連番なので、この結果はフィンガープリントごとに
ファイル間で最大の件数を持つファイルの内容と一致する（累積スナップショット同士は
内容が重なり合うため、単純な合算は行わない）。

### 4.3 `entry_key`

カード会社固有の取引IDがある場合は、そのIDを優先する。

```text
entry_key = SHA-256(import_source_id | external_id)
```

固有IDがない場合は、フィンガープリントと出現番号から生成する。

```text
entry_key = SHA-256(import_source_id | fingerprint | occurrence)
```

取込元の表示名やファイル名はキーに含めない。同じカードの取込元IDは継続して使用する。

### 4.4 累積スナップショットの差分

同じフィンガープリントについて、登録済み件数を `m`、今回指定した1件以上のファイルを
統合した後の件数（4.2節参照）を `n` とする。

- `n > m`: `occurrence = m + 1 ... n` を新しい明細として処理する。
- `n = m`: すべて登録済みとして処理する。
- `n < m`: 既存の明細や取引を削除せず、今回のスナップショットから明細が減ったことを
  プレビューに警告する。

例えば、月途中のファイルに同一フィンガープリントが1件、月末のファイルに2件ある場合、
月末のインポートでは `occurrence = 1` を登録済みとし、`occurrence = 2` だけを新規処理する。

インポートは追加と紐付けのみを行う。累積スナップショットから消えた明細を根拠に、既存取引を
自動削除しない。

## 5. 手入力取引との照合

### 5.1 候補条件

未登録の明細エントリーについて、次の条件をすべて満たす取引を候補にする。カード/現金といった
支払元の区別は設けないため、条件を満たすすべての手入力取引が候補になりうる。

- 同じユーザーである。
- `date`、`amount`、`type` が一致する。
- `source = 'manual'` である。
- `statement_entries` がまだ紐付いていない。

### 5.2 候補の決定

候補を次の順序で評価する。

1. 手入力取引に `description` があり、正規化した明細名まで一致する候補が1件なら自動で紐付ける。
2. 明細名まで一致する候補がなく、基本条件に一致する候補が1件だけなら自動で紐付ける。
3. 基本条件に一致する候補がない場合は、新しい取引を作成する。
4. 候補が複数ある場合は自動で選ばず、プレビューでユーザーに選択を求める。

候補が複数ある場合、ユーザーは既存取引への紐付けまたは新規取引の作成を選択する。未解決の
候補を含む状態ではインポートを確定しない。

### 5.3 紐付け時の更新

既存の手入力取引へ紐付ける場合は、次のように扱う。

- 取引行を新しく作成しない。
- 手入力済みのジャンルとメモを維持する。
- `description` が未設定の場合だけ、カード明細名を設定する。
- `source = 'manual'` を維持する。
- `statement_entries.transaction_id` に既存取引IDを設定する。

対応する手入力取引がない場合は、ジャンル辞書でジャンルを推定した `source = 'import'` の取引を
作成し、その取引IDを明細エントリーへ設定する。

## 6. インポートフロー

### 6.1 プレビュー

1. ユーザーが取込元と、累積型のCSV/PDFを1件以上選択する。
2. 取込元の `format_key` に対応するパーサーでファイルごとに明細を読み取る。
3. 明細を正規化し、フィンガープリント、`occurrence`、`entry_key` を算出する。
   複数ファイルを指定した場合は4.2節の手順で1つの明細リストに統合する。
4. 登録済みの明細エントリーと比較する。
5. 未登録明細について手入力取引との候補照合を行う。
6. 各行を次のいずれかとして表示する。
   - 登録済み
   - 手入力取引に紐付け予定
   - 新規取引として作成予定
   - 要確認
7. 同一フィンガープリントの件数が登録済み件数より減っている場合は警告する。

### 6.2 確定

確定処理の直前に、登録済み判定と候補条件をサーバー側で再評価する。クライアントから渡された
取引ID、ジャンルID、取込元IDは、認証ユーザーが所有する値か検証する。

サーバーアクション内で次の処理を行を1件ずつ逐次実行する。

1. 登録済みの `entry_key` をスキップする。
2. 指定された手入力取引を条件付きで更新し、明細エントリーを紐付ける。
3. 対応する取引がない明細の取引を作成する。
4. `statement_entries` を作成する。
5. `import_batches` に結果を記録する。複数ファイルを指定した場合は、ファイルごとに
   1行ずつ記録する。

`statement_entries` の一意制約（`entry_key`、`transaction_id`）を最終防衛線とし、同じインポートを
同時に確定した場合は一意制約違反となった行をスキップして扱う。

## 7. 編集と削除

- 明細が紐付いた取引の日付・金額・種別を変更すると明細との不整合が生じるため、
  通常の編集では変更できないようにする。
- ジャンル、メモ、表示用の明細名は編集できる。
- `statement_entries.transaction_id` は `on delete restrict` とし、明細が紐付いた取引を通常の
  取引削除から削除できないようにする。
- 明細エントリーと取引を明示的に両方削除した場合、同じ累積明細の再インポートでは新しい取引として
  作成される。

## 8. セキュリティと整合性

- `statement_entries` を含む公開スキーマの全テーブルでRLSを有効にする。
- ポリシーは `to authenticated` と `(select auth.uid()) = user_id` を組み合わせる。
- 更新ポリシーには `using` と `with check` の両方を設定する。
- 新しいテーブルには、`authenticated` に必要な権限を明示的に付与する。
- `import_sources`、`transactions`、`statement_entries` の参照先が同じユーザーに
  属することを、サーバーアクション内の検証で保証する。
- `service_role` キーをクライアントへ公開しない。

## 9. 受け入れ条件

- 手入力した取引と明細が一致すると、取引数を増やさずに紐付く。
- 対応する手入力取引がない明細だけが新しい取引になる。
- 月途中と月末の累積明細を順番に取り込むと、月末までに増えた明細だけが追加される。
- 同じ累積明細を何度取り込んでも、取引と明細エントリーが増えない。
- 同日・同額・同一明細名の取引が複数あっても、累積件数分を保持する。
- 候補が複数ある明細は、ユーザーが選択するまで自動で紐付かない。
- 同じインポートを同時に確定しても重複しない。
- 別ユーザーのアカウント、取引、ジャンル、取込元を参照できない。
